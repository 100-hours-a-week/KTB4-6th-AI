# ADR-0011: FE에서 PCM을 전송해 실시간 오디오의 디코더 상태 의존성을 제거한다

## Status

Accepted

---

## Context

[ADR-0006](0006-live-audio-decoding-location.md)과 [ADR-0007](0007-live-audio-decoder-ffmpeg-subprocess.md)은 FE가 MediaRecorder의 압축 음성을 BE로 보내고, AI가 ffmpeg로 PCM으로 변환하도록 결정했다. [ADR-0008](0008-live-audio-stream-decoder-and-ai-session-lifetime.md)은 AI·STT 세션을 유지하면서 새 녹음 스트림마다 디코더를 교체하도록 했다.

V2 요구사항에 따라 서버를 분산하고 scale-out·scale-in을 도입하면서, 재연결 시 기존 스트림을 처리하던 인스턴스와 디코더가 계속 남아 있다는 전제를 유지하기 어려워졌다. 새 인스턴스의 디코더에 미확인 청크부터 재전송하면 이전 헤더와 디코딩 상태가 없어 음성을 처리하지 못하거나 일부를 누락할 수 있다. MediaRecorder가 나눠 반환하는 Blob은 개별 재생 가능성이 보장되지 않는다. ([W3C MediaStream Recording, §2.3](https://www.w3.org/TR/2026/WD-mediastream-recording-20260316/#mediarecorder-methods))

2026-10-16 부하테스트와 로컬 재현 실험에서는 `decoder.reset`의 ffmpeg 초기화가 다른 세션의 준비 처리를 지연시키는 병목 또한 확인되었다.([실험 조건·결과: 이슈 #98](https://github.com/100-hours-a-week/KTB4-6th-AI/issues/98))

따라서 실시간 전송 형식을 다시 결정한다. 서버 교체 이후에도 이전 디코더 상태를 복원하지 않고 청크를 처리할 수 있는 것이 주된 요구사항이며, AI의 ffmpeg 자원 부담 감소는 부차적인 효과이다.

이 ADR은 ADR-0006·0007을 대체하고, ADR-0008·[ADR-0009](0009-recording-file-storage-location.md)의 압축 스트림·디코더 전환 전제를 변경한다. AI·STT 세션의 수명과 FE의 원본 보관·파일 업로드 책임은 별도 결정으로 유지한다.

---

## Decision Drivers

- **서버 교체 후에도 이전 헤더·디코더 상태 없이 오디오를 처리한다.** 서버 장애, scale-out·scale-in과 재연결로 처리 인스턴스가 달라져도 미확인 청크를 다시 입력하고 녹음 데이터 처리를 문제 없이 이어나갈 수 있어야 한다.
- **복구를 위해 관리해야 하는 스트림 상태를 줄인다.** FE·BE·AI가 이전 압축 스트림의 복구와 새 디코더 시작 순서를 함께 맞추는 부담을 줄인다.
- **동시 녹음 시작 부하를 줄인다.** 부하시험에서 확인한 ffmpeg 초기화 병목을 제거한다.
- **FE와 네트워크에 옮겨지는 비용을 감수할 수 있어야 한다.** 브라우저의 PCM 생성·리샘플링과 증가하는 전송량을 함께 고려한다.

---

## Considered Options

### A. 압축 전송을 유지하고 서버에서 스트림 상태를 보존·복구한다

FE는 MediaRecorder 청크를 보내고 AI가 디코딩한다. 기존 디코더를 가진 인스턴스로 연결을 유지하거나, 새 인스턴스가 디코딩을 재개할 수 있도록 초기화 정보와 필요한 이전 오디오·재개 경계를 보관하고 재전송한다.

**장점**

- FE의 MediaRecorder 기반 수집을 유지하고, PCM보다 적은 오디오 전송량을 사용할 수 있다.
- 브라우저별 입력 형식과 STT 입력 규격의 차이를 AI에서 처리한다.

**단점**

- 기존 인스턴스에 연결을 유지하는 방법만으로는 해당 인스턴스가 사라진 뒤의 복구를 해결하지 못한다.
- 새 디코더에서 복구하려면 헤더뿐 아니라 재개 가능한 경계와 필요한 이전 입력도 관리해야 한다. 청크 순번만으로 복구 지점을 정할 수 없다.
- 디코더 위치·수명과 압축 스트림 복구가 서버 확장·축소 정책에 계속 연결된다.

### B. FE에서 고정 규격 PCM을 생성해 전송한다

FE가 Web Audio 기반으로 음성 샘플을 얻어 16 kHz·mono·signed 16-bit little-endian raw PCM으로 전송한다. BE는 PCM을 중계하고 AI는 수신한 바이트를 STT에 직접 전달한다.

**장점**

- 규격과 2바이트 샘플 경계를 지킨 청크는 이전 컨테이너 헤더나 디코더 상태 없이 처리할 수 있다.
- 처리 인스턴스가 바뀌어도 압축 스트림의 초기화 정보와 디코더를 복원할 필요가 없다.
- 실시간 AI에서 ffmpeg 프로세스와 `decoder.reset / decoder.ready` 절차가 사라진다.

**단점**

- FE가 PCM 생성·리샘플링·샘플 경계 처리를 맡고, 브라우저와 기기별 동작을 검증해야 한다.
- 오디오 데이터만 초당 32,000바이트, 시간당 약 115.2 MB가 필요하다. 이는 `16,000 samples/s × 1 channel × 2 bytes`로 계산한 값이며, 통신 오버헤드는 제외한다.
- 공통 PCM 입력 규격의 변경은 FE에도 영향을 준다. 저장한 원본과 최종 파일을 만드는 FE 경로도 전송 형식에 맞춰 확인해야 한다.

---

## Decision

**B안을 선택한다. FE가 고정 규격 PCM을 생성해 FE → BE → AI 구간으로 전송하고, 실시간 AI의 ffmpeg 디코더를 제거한다.**

V2 분산 환경에서 기존 디코더를 가진 인스턴스에 의존하는 구조보다, 새 인스턴스에서도 이전 디코더 상태 없이 오디오를 받을 수 있는 구조를 우선한다. A안은 압축 전송량의 이점을 유지하지만 인스턴스 교체 시 압축 스트림의 복구 상태를 추가로 관리해야 한다. FE 구현 부담과 전송량 증가를 감수하고 이 의존성을 제거한다.

```text
FE: 음성 수집·PCM 생성 → BE: PCM 중계 → AI: PCM 수신 → STT
```

- 전송 규격은 16 kHz·mono·signed 16-bit little-endian raw PCM이며, 각 청크는 2바이트 샘플 경계를 지킨다. 기존 [STT 입력 규격](../../src/meety_ai/recording/stt_client.py)과 맞춘다.
- AI는 `session.ready` 이후 `audio.meta`와 PCM binary를 받고, [RecordingSession](../../src/meety_ai/recording/session.py)에서 검증한 바이트를 STT로 직접 전달한다. `decoder.reset / decoder.ready`는 제거한다.
- PCM 전환으로 제거하는 것은 압축 스트림의 헤더·디코더 상태 의존성이다. 순번·ACK·중복 제거·마지막 청크 확인과 STT 세션·전사 시간축 복구는 #102의 별도 작업으로 남는다.
- FE의 원본 영속 보관·최종 파일 변환·업로드 책임은 유지한다. 저장 형식과 변환 세부 구현은 FE에서 확인하며, 사후 화자 분리용 Modal의 파일 변환은 이 결정의 대상이 아니다.

## Consequences

### Positive

- 서버가 교체돼도 이전 디코더를 찾아 연결하거나 압축 스트림 상태를 복원할 필요가 없다.
- 청크 재전송 시 녹음 스트림별 헤더·디코더 전환 순서에 대한 조율이 줄어든다.
- 실시간 AI에서 ffmpeg 초기화 병목과 프로세스·실행 파일 관리 부담을 제거한다.

### Negative

- FE가 PCM 생성과 리샘플링의 정확성을 책임지고, 오디오 전송량이 증가한다.
- PCM 원본을 보관하는 경우 브라우저 저장 용량도 증가한다. 파일 변환 결과와 STT 입력의 샘플·시간축이 일치하는지 확인해야 한다.
- PCM만으로 무손실 재연결이나 STT 상태 복구가 완성되지는 않는다. ACK와 재전송·중복 제거 정책이 별도로 필요하다.
- AI의 PCM 직접 전달은 로컬 테스트로 확인했지만, PCM 전환 후 동일한 50세션 부하시험과 실제 FE–BE–AI 연동·모바일·장시간 녹음은 후속 검증이 필요하다. 서버 자원 절감량과 기기별 처리 비용은 아직 측정하지 않았다.

---

## Reconsideration Conditions

- 모바일·장시간 녹음에서 PCM 전송량이나 브라우저 처리·저장 부담 때문에 녹음이 반복적으로 실패하면, 독립적으로 디코딩 가능한 압축 단위 전송과 구간별 업로드를 비교한다.
- 서버 교체 이후 청크를 독립적으로 복구할 수 있는 압축 전송 방식이 검증되고 네트워크 비용이 주요 병목이 되면 압축 전송을 다시 비교한다.
- STT 입력 요구가 바뀌어 공통 PCM 규격으로 대응하기 어려워지면 FE–AI 입력 규격과 AI의 추가 변환 책임을 재검토한다.
