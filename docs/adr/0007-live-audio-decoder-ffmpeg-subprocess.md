# ADR-0007: 실시간 녹음 음성을 ffmpeg 서브프로세스로 디코딩한다

## Status

Accepted

---

## Context

[ADR-0006](0006-live-audio-decoding-location.md)에 따라 실시간 AI는 BE가 전달한 압축 음성(WebM+Opus, 조각 MP4+AAC)을 16 kHz·mono·signed 16-bit little-endian PCM으로 변환한다. 이 ADR은 그 변환에 사용할 도구를 결정한다.

녹음 음성은 한 번에 완성된 파일로 오지 않는다. 녹음 세션 동안 WebSocket으로 청크가 계속 들어오고, 실시간 AI 서버는 녹음이 끝나기 전에 PCM을 STT에 실시간으로 넘겨야 한다. 실시간 AI 서버는 여러 녹음 세션을 한 프로세스에서 동시에 처리한다.

```text
BE ──WebSocket 청크──▶ 녹음 세션 ──▶ [디코더] ──PCM──▶ STT
                           (연속 입력)      무엇으로?
```

---

## Decision Drivers

- **연속으로 들어오는 음성을 녹음 종료 전에 변환할 수 있는가?** 녹음 도중 들어오는 청크를 처리해 회의가 진행되는 동안 PCM을 STT에 전달해야 한다.
- **한 회의의 음성 변환이 다른 회의의 처리를 지연시키지 않는가?** 여러 회의를 동시에 처리하므로, 디코딩 대기가 공용 asyncio 이벤트 루프를 막아 다른 회의의 오디오 수신이나 전사 결과 전달을 늦추면 안 된다.
- **필요한 음성 변환을 적은 연결 코드로 구현할 수 있는가?** 입력 전달과 변환 결과 수신에 필요한 코드가 단순해야 한다. 프레임 단위 제어나 메타데이터 처리는 당장 필요하지 않다.
- **연결이 끊겨도 디코더 자원을 정리할 수 있는가?** 명시적인 종료 신호 없이 연결이 끊겨도 해당 세션의 디코더가 남지 않아야 한다.

---

## Considered Options

### A. ffmpeg CLI 서브프로세스

녹음 세션마다 `asyncio.create_subprocess_exec()`로 ffmpeg 프로세스를 띄운다. 청크는 stdin에 쓰고, 별도 task가 stdout의 PCM을 읽어 콜백으로 넘긴다. 정상 종료 시 stdin을 닫아 잔여 PCM을 받고, 연결이 끊기면 프로세스를 kill한다.

**장점**

- **WebSocket 청크 수신 구조와 그대로 맞는다.** 청크가 들어올 때마다 stdin에 쓰면 되고, 입력을 모아 두는 별도 버퍼가 필요 없다.
- **이벤트 루프를 막지 않는다.** asyncio 서브프로세스 파이프로 입출력을 비동기로 처리한다.
- **정리가 단순하다.** 연결이 끊기면 `kill()`과 `wait()`로 프로세스를 종료·회수한다.
- **디코더 프로세스의 비정상 종료가 격리된다.** ffmpeg가 비정상 종료해도 AI 서버 프로세스는 유지되므로 해당 세션의 오류로 처리할 수 있다.

**단점**

- **배포 이미지에 ffmpeg 실행 파일이 필요하다.** `uv sync`만으로는 설치되지 않는다.
- **세션마다 프로세스가 하나씩 생긴다.** 스레드보다 무거워 동시 녹음 수에 영향을 준다.
- **디코딩 내부 상태를 직접 다루기 어렵다.** 오류는 stderr와 종료 코드 등 프로세스가 내보내는 정보를 통해 파악해야 한다.

### B. PyAV

FFmpeg 라이브러리를 Python에서 직접 호출한다. PyPI wheel에 FFmpeg가 포함돼 있어 별도 설치가 필요 없다. 청크를 file-like 객체로 감싸 `av.open()`에 넘기고, 디코딩한 프레임을 `AudioResampler`로 PCM으로 변환한다.

**장점**

- **배포가 간단하다.** 의존성 추가만으로 FFmpeg를 사용할 수 있다.
- **세션마다 별도 프로세스를 생성하지 않는다.** 서버 프로세스 안에서 디코딩을 실행할 수 있다.
- **프레임 단위로 제어할 수 있다.** 타임스탬프, 코덱 정보 등 디코딩 과정의 정보를 직접 다룰 수 있다.

**단점**

- **스트리밍 입력에 별도 어댑터가 필요하다.** PyAV는 필요한 만큼 데이터를 끌어가는 방식이라, 청크를 쌓아 두고 데이터가 모자라면 기다리는 file-like 객체를 직접 구현해야 한다.
- **스레드 분리가 필요하다.** 동기 API가 데이터를 기다리는 동안 이벤트 루프를 막으므로 디코딩을 스레드로 옮기고, 스레드의 PCM을 asyncio 콜백으로 다시 넘기는 연결 코드가 필요하다.
- **입력 대기 중인 작업의 종료를 직접 설계해야 한다.** 연결이 끊기면 입력 어댑터의 대기를 해제하고 디코딩 작업을 종료한 뒤 자원을 회수해야 한다.
- **네이티브 라이브러리의 프로세스 충돌이 서버에 영향을 준다.** Python 예외와 달리 프로세스 자체가 종료되는 장애는 같은 서버의 다른 세션에도 영향을 준다.

---

## Decision

**A안을 선택해 녹음 세션마다 ffmpeg 서브프로세스로 압축 음성을 PCM으로 변환한다.**

- 지금 필요한 것은 청크를 넣으면 PCM이 나오는 변환기다. A안은 WebM·MP4 해석부터 리샘플링까지 한 번의 호출로 처리하고, WebSocket 청크 수신 구조에 추가 어댑터 없이 연결된다.
- 두 안 모두 녹음 도중 디코딩할 수 있다. A안은 asyncio 파이프로 입출력을 처리하고 프로세스를 종료·회수할 수 있지만, B안은 입력 어댑터·스레드 연결·대기 해제와 종료 처리가 추가로 필요하다.
- 현재는 연결 코드와 자원 정리의 단순성을 우선하고, A안의 실행 파일 배포와 세션당 프로세스 비용을 감수한다.
- B안의 프레임 단위 제어는 현재 요구사항에 필요하지 않다.

---

## Consequences

### Positive

- 별도 입력 어댑터나 스레드 간 전달 코드 없이 청크 입력과 PCM 출력을 연결할 수 있다.
- 비동기 파이프 입출력으로 디코딩 대기가 asyncio 이벤트 루프를 막지 않게 할 수 있다.
- 연결 종료 시 해당 세션의 디코더 프로세스를 독립적으로 종료·회수할 수 있다.
- 디코더 프로세스가 비정상 종료해도 AI 서버 프로세스는 유지된다.

### Negative

- 배포 이미지에 ffmpeg와 필요한 코덱(libopus, AAC)을 포함해야 한다.
- 세션마다 프로세스를 생성하므로 동시 녹음 수가 늘수록 프로세스 실행에 필요한 자원도 늘어난다.

---

## Reconsideration Conditions

- 세션당 프로세스 비용이 동시 녹음 확장의 병목이 되면 B안을 재검토한다.
- 타임스탬프 활용, 부분 디코딩 등 프레임 단위 제어가 필요해지면 B안을 재검토한다.
- 배포 환경에서 ffmpeg 실행 파일 관리가 반복적인 문제가 되면 B안을 재검토한다.
