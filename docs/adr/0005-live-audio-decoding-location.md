# ADR-0005: 실시간 녹음 음성을 AI 서버에서 PCM으로 변환한다

## Status

Accepted 

---

## Context

녹음 담당자의 브라우저는 MediaRecorder로 회의 음성을 녹음하고, BE를 거쳐 실시간 AI로 전달한다.  
브라우저마다 다른 녹음 형식을 사용한다. Chromium 계열(Chrome, Edge, Whale)은 WebM+Opus를, Safari(iOS)는 MP4+AAC를 사용한다.

실시간 AI는 받은 음성을 외부 STT로 전사한다. 사용 예정인 ElevenLabs 실시간 STT는 `pcm_8000`~`pcm_48000`과 `ulaw_8000`만 입력으로 받는다. 따라서 압축 음성을 STT에 그대로 전달할 수 없고, 전체 프로세스 중 한 곳에서 PCM으로 변환할 필요가 있다.

```text
Recorder Browser ──▶ BE ──▶ 실시간 AI ──▶ External STT
  (MediaRecorder)                                (PCM만 입력)
         ▲ 어느 구간에서 PCM으로 바꿀 것인가
```

---

## Decision Drivers

- **BE는 음성 내용을 다루지 않는다.** BE는 음성을 전달만 하고 음성 처리는 AI가 맡는다.
- **녹음이 끝나기 전에 PCM을 얻어야 한다.** 회의 종료 후가 아닌, 회의 진행 중에 전사를 제공하기 위해 녹음이 진행 중인 상황에서도 실시간 PCM 변환이 가능해야 한다.
- **STT 공급자와 입력 규격에 FE·BE가 의존하지 않는다.** STT 공급자는 아직 확정되지 않았고 비용·rate limit·부가기능에 따라 바뀔 수 있으며, 공급자마다 요구하는 입력 규격이 다르다. Provider 별 rate limit으로 인해 한번에 여러 공급자를 사용할 가능성도 존재한다.
- **브라우저별 코덱 차이를 한 곳에서 대응한다.** 입력 형식이 늘거나 바뀌어도 한 곳만 대응한다.
- **브라우저 - BE 구간은 압축 음성으로 전송한다.** 녹음 담당자의 네트워크 사용량을 줄인다.

---

## Considered Options

### A. 브라우저에서 PCM 생성

MediaRecorder 대신 Web Audio API(AudioWorklet)로 원시 음성 샘플을 받아 16 kHz로 리샘플링한 PCM을 전송한다. BE와 실시간 AI는 PCM을 그대로 전달한다.

**장점**

- **디코딩이 필요 없다.** 서버에 디코더 의존성과 디코딩 CPU 비용이 생기지 않는다.
- **형식 차이가 사라진다.** 모든 브라우저가 같은 PCM을 보내므로 서버가 입력 형식을 구분하지 않아도 된다.

**단점**

- **전송량이 늘어난다.** 16 kHz mono PCM은 32 KB/s다. ffmpeg 기본 설정으로 인코딩한 10초 샘플은 WebM+Opus 약 10.3 KB/s, MP4+AAC 약 9.1 KB/s로, PCM이 약 3.1~3.5배 크다.
- **프론트엔드 작업이 늘어난다.** AudioWorklet 구현, 리샘플링, 브라우저별 Web Audio 동작 차이를 프론트엔드가 맡는다.
- **STT 공급자 변경에 영향을 받는다.** STT API provider가 변경되어 요구 입력 규격이 달라질 경우 FE에서 그 규격에 맞춰 기능을 수정해야 한다.

### B. BE에서 변환

BE가 압축 음성을 받아 PCM으로 변환한 뒤 실시간 AI로 전송한다.

**장점**

- **브라우저–BE 구간은 압축 음성을 유지한다.** 녹음 담당자의 전송량은 늘지 않는다.
- **실시간 AI가 단순해진다.** AI 서버는 PCM만 받아 STT로 전달한다.

**단점**

- **기존 팀 역할 경계가 무너진다.** 음성 데이터의 전달·저장만 담당하던 백엔드가 음성 처리 역할을 맡게 된다.
- **BE 작업과 의존성이 늘어난다.** BE 실행 환경에 디코더와 형식별 처리 로직을 추가해야 한다.
- **BE–AI 구간 전송량이 늘어난다.** 내부 구간이라 녹음 담당자에게는 영향이 없지만 PCM 크기만큼 트래픽이 증가한다.
- **STT 공급자 변경에 영향을 받는다.** STT API provider가 변경되어 요구 입력 규격이 달라질 경우 BE에서 그 규격에 맞춰 기능을 수정해야 한다.

### C. AI 서버에서 변환

BE는 받은 압축 음성을 그대로 실시간 AI로 전달한다. 실시간 AI는 녹음 세션마다 디코더를 두고 PCM으로 변환해 STT로 전송한다.

**장점**

- **형식 차이를 STT와 가장 가까운 곳에서 흡수한다.** 입력 형식 대응과 STT 입력 규격 변환이 한 서비스 안에 있다.

- **STT 공급자 변경이 FE·BE로 번지지 않는다.** FE·BE와의 계약은 MediaRecorder 출력이고, STT가 요구하는 입력 규격은 AI 서버의 변환 설정에만 있다. A·B안에서는 STT 입력 규격이 브라우저나 BE 코드에 들어간다.

**단점**

- **AI 서버가 디코딩 비용을 진다.** 녹음 세션마다 디코딩 CPU와 메모리를 사용한다.

- **입력 형식 변화에 AI 서버가 대응한다.** 브라우저가 보내는 형식이 바뀌면 AI 서버를 수정해야 한다.

---

## Decision

**C안을 선택해 실시간 녹음 음성을 AI 서버에서 PCM으로 변환한다.**

- A안은 서버의 디코딩 부담을 없앨 수 있지만 브라우저–BE 구간 전송 트래픽을 크게 증가시키고, FE에서 STT 공급자에 의존성을 갖게 된다.
- B안은 녹음 담당자의 전송량을 유지하지만 BE가 음성을 다루지 않는다는 역할 경계를 위반하며, A안과 마찬가지로 STT 공급자 의존성을 BE에서 갖게 된다.
- C안은 AI 서버를 브라우저 녹음 형식에 묶는 대신 STT 입력 규격으로부터 FE·BE를 분리한다. 브라우저 녹음 형식은 MediaRecorder가 지원하는 소수의 형식으로 안정적인 반면, STT 공급자는 비용·rate limit·부가기능에 따라 바뀔 가능성이 더 높다고 판단했다.

---

## Consequences

### Positive

- 브라우저와 BE는 녹음 형식을 몰라도 된다.
- STT 공급자나 입력 규격이 바뀌어도 AI 서버만 수정하면 된다.
- 입력 형식이 추가되거나 바뀌어도 AI 서버만 수정하면 된다.
- 브라우저–BE 구간은 압축 음성으로 전송된다.

### Negative

- 실시간 AI의 동시 녹음 수가 디코딩 CPU·메모리에 제한된다. 
- 배포 이미지에 디코더를 포함해야 한다.
- 디코딩 실패는 데이터가 AI 서버까지 가야만 감지되며, BE는 오류 응답으로만 알 수 있다.

---

## Reconsideration Conditions

- STT가 WebM·MP4 등 압축 음성을 직접 입력으로 받게 되면 변환 단계 자체를 재검토한다.
- 동시 녹음 증가로 AI 서버의 디코딩 비용이 병목이 되면 A안(브라우저 PCM 생성)을 재검토한다.
- 프론트엔드가 Web Audio 기반 녹음으로 전환하면 A안을 재검토한다.
