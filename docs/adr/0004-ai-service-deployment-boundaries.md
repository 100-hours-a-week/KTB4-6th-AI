# ADR-0004: AI 서비스를 실시간·회의 분석·GPU 추론 단위로 분리한다

## Status

Accepted — 2026-09-09

---

## Context

Meety V3는 회의 중 실시간 전사·QnA·보이스 에이전트를 제공하고, 종료 후 화자 분리·요약·지표·리포트를 생성한다.

이 기능들을 하나의 AI 서비스에서 실행하면 분석 작업의 부하나 배포가 진행 중인 회의의 오디오 처리와 연결에 영향을 줄 위험이 있다. 반대로 전사·QnA·보이스 에이전트를 기능별 서비스로 나누고 Backend가 각각 직접 연결하면, 서비스별 연결·인증·오류·종료 상태를 관리해야 하므로 운영 복잡도가 커진다.

따라서 실시간 회의에 대한 영향을 줄이면서 Backend의 연결 관리 부담을 제한할 실행·배포 경계를 결정한다. GPU 실행 플랫폼 자체의 선정은 이 ADR의 비교 범위에서 제외하며, 각 대안에서 GPU 화자 분리는 별도로 실행하는 것을 공통 전제로 한다.

---

## Decision Drivers

- **실시간 회의 보호를 우선한다.** 종료 후 분석 작업의 부하와 배포가 실시간 처리에 미치는 영향을 제한한다.
- **Backend 연결 관리의 복잡도를 제한한다.** 회의 중 기능은 기존 연결을 공유해 별도로 관리해야 할 통신 경로와 상태를 줄인다.
- **실행 환경의 차이를 반영한다.** GPU 모델 실행 환경을 외부 API 중심의 AI 서비스와 분리한다. 구체적인 GPU 공급자 선정은 별도 판단으로 둔다.

---

## Considered Options

### A. AI 서비스 하나와 별도 GPU 추론

전사·QnA·보이스 에이전트·요약·지표·리포트를 하나의 AI 서비스에서 처리한다. Backend는 회의 중 기능에 WebSocket을, 종료 후 분석에 HTTP를 사용하며 두 요청 모두 같은 AI 서비스로 전달한다. GPU가 필요한 화자 분리는 Modal에서 별도로 실행한다.

**장점**

- **배포와 운영 구성이 단순하다.** 하나의 AI 서비스에 대해 배포 설정, 로그, 상태 확인, 장애 대응 체계를 관리하면 된다.
- **공통 코드를 함께 변경하기 쉽다.** 전사 데이터 구조, 공급자 연동, LLM 호출 로직 등을 같은 실행 환경에서 사용하므로 서비스 간 버전 호환성을 관리하는 부담이 적다.
- **초기 자원 배분이 단순하다.** 실시간용·분석용 처리 용량을 미리 나누지 않고 하나의 서비스에서 요청을 처리할 수 있다.

**단점**

- **실시간과 분석이 프로세스 자원을 공유한다.** 분석 과정의 CPU 처리나 메모리 사용이 커지면 오디오 수신·전사 이벤트 처리에 영향을 줄 수 있다. 실제 영향은 비동기 처리 방식과 부하에 따라 달라진다.
- **분석 변경도 실시간 서비스 배포에 포함된다.** 요약·리포트 코드만 수정해도 회의 연결을 유지하는 프로세스가 배포 대상이 되므로 회의 운영 시간을 고려해야 한다.
- **기능별 확장이 어렵다.** 분석 요청만 늘어나도 통합 서비스 전체를 확장하게 된다. 특정 기능에 필요한 자원만 조절하기 어렵다.
- **프로세스 장애의 영향 범위가 넓다.** 분석 중 메모리 부족 등으로 프로세스가 종료되면 같은 프로세스의 실시간 회의 연결도 영향을 받는다.

### B. 실시간·회의 분석·GPU 추론 분리

전사·질문 STT·QnA·TTS는 실시간 AI 서비스에서 처리하고, 화자 결합·요약·지표·리포트는 회의 분석 AI 서비스에서 처리한다. GPU 화자 분리는 Modal에서 실행한다. Backend는 실시간 AI와 회의별 WebSocket을 공유하고, 분석 AI에는 HTTP로 작업을 요청한다.

**장점**

- **분석과 실시간의 실행 경계를 나눌 수 있다.** 분석 작업의 CPU·메모리 사용을 별도 프로세스에서 관리하므로 같은 프로세스 안에서 발생하는 간섭을 줄일 수 있다.
- **분석 서비스를 독립적으로 배포할 수 있다.** 요약·지표·리포트 변경을 위해 실시간 회의 연결을 담당하는 프로세스를 재시작할 필요가 없다.
- **실제 부하 특성에 맞춰 확장할 수 있다.** 실시간 서비스는 활성 회의 수와 전사 지연을, 분석 서비스는 작업 대기량과 처리시간을 기준으로 용량을 조절할 수 있다.
- **회의 중 기능의 연결 관리가 통합된다.** 전사·QnA·보이스 에이전트가 기존 회의별 WebSocket을 공유하므로 Backend가 기능별 연결과 수명주기를 따로 관리할 필요가 없다.
- **GPU 의존성을 별도로 관리한다.** 화자 모델과 실행 환경을 변경해도 실시간·분석 서비스에 GPU 런타임을 함께 배포하지 않아도 된다. 이는 GPU를 별도로 실행하는 세 대안의 공통 특성이다.

**단점**

- **단일 서비스보다 운영 대상이 늘어난다.** 실시간·분석 서비스 각각의 배포, 상태 확인, 로그와 자원 설정을 관리해야 한다.
- **전사와 QnA·보이스 에이전트 사이의 간섭은 남는다.** 같은 실시간 서비스에 있기 때문에 task 분리와 기능별 동시성·버퍼 제한이 필요하다.
- **공유 WebSocket의 이벤트 처리가 복잡해진다.** 회의 오디오, 질문 오디오, 답변, TTS를 식별해야 하며, 큰 출력이나 느린 작업이 다른 메시지를 지연시키지 않도록 제어해야 한다.
- **회의 중 기능을 개별 배포·확장할 수 없다.** QnA만 변경하거나 음성 질문 요청만 증가하더라도 실시간 서비스 전체가 배포·확장 단위가 된다.
- **서비스 분리만으로 자원·장애가 완전히 격리되지는 않는다.** 같은 호스트에 배치하거나 같은 외부 공급자를 사용하면 자원 경합과 공급자 장애 영향을 공유할 수 있다.

### C. 기능별 서비스 분리

전사·QnA·보이스 에이전트·종료 후 분석을 각각의 서비스로 구성한다. Backend가 각 서비스에 직접 연결하고, 보이스 에이전트는 답변 생성을 위해 QnA 서비스와 연동한다. GPU 화자 분리는 Modal에서 실행한다.

**장점**

- **기능별 배포가 가능하다.** QnA 프롬프트나 음성 응답 기능을 변경할 때 전사 서비스를 함께 배포하지 않아도 된다.
- **기능별 부하에 맞춰 확장할 수 있다.** 전사는 활성 녹음 수, QnA는 질문 요청량, 보이스 에이전트는 음성 질문 처리량에 맞춰 용량을 조절할 수 있다.
- **프로세스 장애의 범위를 더 작게 나눌 수 있다.** QnA 서비스가 종료돼도 전사 프로세스는 계속 실행할 수 있다. 다만 QnA에 의존하는 음성 답변 기능은 영향을 받는다.
- **기능별 개발과 운영 책임을 독립적으로 둘 수 있다.** 담당 팀과 배포 주기가 달라지는 경우 각 서비스가 자체 일정으로 변경하기 쉽다.

**단점**

- **Backend의 연결·상태 관리가 늘어난다.** 기능별 통신 방식에 따라 연결 설정, 인증, 타임아웃, 재연결, 오류 처리를 각각 관리해야 한다.
- **한 회의의 상태를 여러 서비스에 일관되게 전달해야 한다.** 회의 종료, 질문 취소, 요청 식별자와 같은 정보를 연관된 서비스에 전달하고, 일부 서비스만 실패한 상황도 처리해야 한다.
- **보이스 에이전트와 QnA 사이에 추가 연동이 필요하다.** 음성 질문을 텍스트로 변환한 뒤 QnA를 호출하고 결과를 TTS로 넘기는 과정에서 서비스 간 오류·취소·기한을 관리해야 한다.
- **공통 데이터 계약의 변경 부담이 커진다.** 전사·질문·근거 형식이 바뀌면 서로 다른 버전으로 배포된 서비스 사이의 호환성을 확인해야 한다.
- **운영·관측 경로가 분산된다.** 한 질문의 실패 원인을 찾기 위해 Backend, 음성 처리, QnA 등 여러 서비스의 로그를 요청 ID로 연결해야 한다.
- **연결을 통합하려면 별도 중계 계층이 필요할 수 있다.** Backend가 하나의 연결만 사용하도록 만들 수는 있지만, 복잡도가 없어지는 대신 연결 중계와 작업 라우팅을 담당하는 구성 요소로 이동한다.

---

## Decision

**B안을 선택해 AI 서비스를 실시간·회의 분석·GPU 추론 단위로 분리한다.**

- **실시간 AI:** 회의 전사·질문 STT·QnA·TTS를 담당하며 Backend와 회의별 WebSocket을 공유한다.
- **회의 분석 AI:** 화자 결합·요약·지표·리포트를 담당하며 Backend의 HTTP 요청에 완료 결과를 반환한다.
- **GPU 추론:** Modal에서 화자 분리를 실행한다.

실시간 회의를 분석 작업의 영향에서 보호하기 위해 A안보다 실행 경계를 분리한다. 다만 C안처럼 회의 중 기능까지 모두 분리하면 Backend의 연결·상태 관리 부담이 커지므로, 전사·QnA·보이스 에이전트는 같은 서비스에 둔다. B안은 분석을 독립적으로 운영하면서 회의 중 기능의 통신을 공유하는 절충안이다.

기존 Wiki ADR-001~003의 통신 방식과 Backend의 작업 상태·결과 저장 책임은 유지한다. 내부 기능 모듈이 각각의 배포 단위를 뜻하지는 않으며, QnA는 실시간 AI와, 요약·지표·리포트는 회의 분석 AI와 함께 배포한다.

---

## Consequences

### Positive

- 분석 서비스의 배포를 위해 실시간 프로세스를 재시작할 필요가 없다.
- 분석 대기량과 활성 회의 수에 따라 각 서비스의 처리 용량을 별도로 조절할 수 있다.
- 전사·QnA·보이스 에이전트가 연결을 공유해 Backend 연동의 복잡도를 제한한다.
- GPU 모델 의존성을 실시간·분석 서비스의 실행 환경에서 분리한다.

이 효과는 목표 구조에서 기대하는 결과이며 실제 지연·처리량·비용 개선을 관측한 것은 아니다.

### Negative

- 배포·관측·서비스 간 계약 관리 대상이 늘어난다.
- QnA나 보이스 에이전트의 변경도 실시간 서비스 전체 배포에 포함된다.
- 실시간 서비스 내부의 부하 간섭을 줄이기 위해 task 분리와 동시성·버퍼 제한이 필요하다.
- 같은 호스트나 외부 공급자를 공유하면 자원 경합과 장애 영향이 남는다.

---

## Reconsideration Conditions

- 실시간 서비스 내부의 부하 제어 후에도 QnA·보이스 에이전트가 전사 지연 목표를 반복적으로 침해하면 기능별 분리를 재검토한다.
- QnA·보이스 에이전트의 잦은 배포가 회의 운영을 제약하면 실시간 서비스의 배포 경계를 재검토한다.
- 요약·지표·리포트 중 특정 기능의 부하가 다른 분석 작업의 허용 대기시간을 지속적으로 초과하면 분석 서비스 내부 분리를 재검토한다.

지연 목표와 허용 대기시간의 수치는 아직 정하지 않았으며, 후속 부하 검증 전에 구체화한다. 비교 실험은 이번 결정에서 수행하지 않고 후속 검증으로 남긴다.
