# ADR-0010: 회의 QnA의 Backend–AI 통신을 HTTP 요청·응답으로 전환한다

## Status

Accepted

---

## Context

[ADR-0002](0002-backend-ai-chatbot-websocket.md)는 실시간 전사용 WebSocket을 재사용해 회의 QnA의 질문과 결과를 전달하도록 결정했다. Backend가 `chat.request`를 보내면 AI가 `chat.accepted`를 반환하고, 답변 생성 후 `chat.completed` 또는 `chat.failed`를 같은 연결로 보내는 방식이다.

이 연결은 녹음과 연결된 수명을 갖는다. 다중 Backend 인스턴스 환경에서 질문을 받은 인스턴스와 녹음용 AI WebSocket을 가진 인스턴스가 다를 수 있어, 기존 방식을 유지하려면 연결을 소유한 인스턴스를 찾아 질문과 결과를 전달해야 한다. 또한 질문에 현재 회의의 확정 전사와 공유 대화 이력을 포함하므로, 큰 질문 메시지의 수신 한도 초과나 같은 연결에서의 전송 지연이 녹음 흐름에도 영향을 줄 수 있다.

[클라우드 V2 서비스 확장 가정](https://github.com/100-hours-a-week/KTB4-6th-wiki/wiki/1.-서비스-확장-MAU-및-RPS-가정)은 V2 도입 후 3년의 목표 MAU를 250,000명, DAU를 100,000명으로 두고, 챗봇 목표·최악 피크를 각각 2.55·3.82 RPS로 산정한다. 전체 서비스 피크는 각각 44.26·88.78 RPS이며, 기존 단일 인스턴스 구성에서 인스턴스 다중화·로드밸런싱·이벤트 버스 도입 등을 검토해야 한다고 제시한다. 이는 실제 트래픽이나 처리 용량 측정이 아닌 성장 시나리오다. 이 ADR에서는 해당 시나리오에 대비해 QnA가 특정 녹음 연결과 인스턴스에 묶이지 않고 분산 환경으로 확장될 수 있어야 한다는 설계 기준으로 사용한다.

이 ADR은 QnA의 Backend–AI 전송 경로, 실행·배포 위치와 결과 전달 책임을 결정한다. QnA는 회의 분석 AI(analysis)의 HTTP API로 제공하고, 실시간 AI(live)는 녹음 WebSocket과 전사를 담당한다. 전사 WebSocket과 Agent의 자료 조회 방식은 유지한다. ADR-0002를 대체하며, [ADR-0004](0004-ai-service-deployment-boundaries.md)의 QnA를 실시간 AI에 통합하는 배포 경계도 변경한다.

---

## Decision Drivers

- **클라우드 V2의 분산 환경 확장에 대비한다.** Backend와 AI 인스턴스를 늘려도 QnA 요청은 녹음 연결의 위치와 독립적으로 분산할 수 있어야 한다. 위키의 챗봇 RPS 가정은 후속 부하 검증의 입력으로 사용하며, HTTP 전환만으로 목표 처리량을 달성했다고 판단하지 않는다.
- **녹음 연결을 소유한 Backend 인스턴스에 의존하지 않는다.** 질문을 처리하는 Backend가 AI 호출과 결과 처리를 맡을 수 있어야 한다.
- **QnA 전송과 녹음 연결의 수명을 분리한다.** 큰 질문 메시지나 QnA 처리 실패가 녹음 WebSocket을 종료시키지 않아야 하며, 녹음 일시정지 중에도 질문할 수 있어야 한다.
- **녹음 처리와 LLM 작업의 실행·배포를 분리한다.** QnA의 자원 사용과 배포가 녹음 연결을 담당하는 프로세스에 영향을 주지 않게 한다. Backend는 QnA·요약·화자 분리 요청에 같은 분석 AI HTTP 주소를 사용한다.
- **기존 책임 경계를 유지한다.** 질문 상태·권한·저장·참가자 전달은 Backend가 맡고, AI에는 영구 job 상태나 결과 전달 재시도를 추가하지 않는다.
- **기존 QnA 계약을 재사용한다.** 현재 전사·공유 대화·추가 자료 조회·답변·근거를 유지하고, 전송 방식 변경에 필요한 차이만 반영한다.

---

## Considered Options

### 1. 기존 녹음 WebSocket에서 QnA 이벤트를 계속 교환한다

Backend가 녹음용 AI 연결로 질문을 전달하고, AI가 접수와 완료·실패 이벤트를 비동기로 반환한다. 다른 Backend 인스턴스가 질문을 받으면 연결 소유 인스턴스까지 전달하는 경로가 필요하다.

**장점**

- 기존 ADR-0002와 기존 QnA 이벤트 처리 구현을 유지할 수 있다.
- 답변 생성이 끝날 때까지 별도의 Backend–AI HTTP 요청을 유지하지 않는다.

**단점**

- 다중 인스턴스에서 질문 전달을 위해 녹음 연결의 소유 위치를 알아야 한다.
- 인스턴스를 늘려도 QnA를 기존 녹음 연결로 전달해야 하므로, 연결 소유 위치 관리와 인스턴스 간 전달 구조를 함께 확장해야 한다.
- 전사와 QnA가 같은 연결의 메시지 한도와 전송 경로를 공유한다.
- 일시정지 중 질문 허용, 녹음 종료 시 작업 취소 등 QnA가 녹음 프로토콜의 상태에 의존한다.

### 2. HTTP 요청을 보내고 최종 결과를 응답으로 받는다

질문을 처리하는 Backend가 전사 스냅샷과 공유 대화를 담아 회의 분석 AI의 `POST /v1/chat`을 호출한다. 분석 AI는 Agent 실행을 기다린 뒤 성공 시 HTTP 200으로 답변·근거를, 실패 시 4xx 또는 5xx로 오류를 반환한다. Backend가 결과를 저장하고 회의방 참가자에게 SSE로 전달한다. AI가 추가 자료를 조회할 때는 기존 내부 HTTP API를 사용한다.

**장점**

- 질문을 받은 Backend에서 AI 호출과 응답 처리를 맡을 수 있어 녹음 연결 소유 인스턴스로 전달할 필요가 없다.
- 요청에 필요한 전사 스냅샷과 대화를 포함하므로, QnA를 처리할 AI 인스턴스를 녹음 연결과 독립적으로 로드밸런싱할 수 있다. 인스턴스 간 QnA 세션 이전이나 연결 소유 정보가 필요하지 않다.
- QnA 요청 크기나 전송 오류가 녹음 WebSocket의 메시지 처리에 직접 영향을 주지 않는다.
- 녹음 연결의 시작·일시정지·종료 상태와 독립된 AI 요청 처리가 가능하다.
- QnA를 분석 AI에 배치해 LLM 작업과 배포를 녹음 프로세스에서 분리한다. 요청에 전사 스냅샷이 있으므로 live의 녹음 상태를 공유할 필요가 없다.
- QnA·요약·화자 분리는 Backend의 기존 분석 AI HTTP 주소를 함께 사용하므로 챗봇 전용 서비스나 호출 주소가 필요 없다.
- AI에 job 저장소, callback, polling API를 추가하지 않고 최종 결과를 전달한다.

**단점**

- 가상 스레드를 사용하지 않고 일반 스레드에서 동기 HTTP 호출을 하는 경우, AI 응답을 기다리는 동안 호출 스레드와 Backend–AI HTTP 연결을 계속 점유한다. 요청이 많아지거나 답변 생성이 길어지면 스레드 풀과 HTTP 연결 풀의 가용 자원이 줄어 후속 요청의 대기 시간이 늘어날 수 있다.
- 최종 결과를 같은 HTTP 요청으로 반환하므로 Backend·AI·프록시의 타임아웃을 맞춰야 한다. 처리 시간이 대기 제한을 넘으면 해당 요청으로 결과를 전달할 수 없다.

### 3. HTTP 202로 접수하고 callback 또는 polling으로 결과를 전달한다

AI가 질문을 job으로 접수하고 즉시 응답한 뒤, 별도 callback으로 결과를 보내거나 Backend가 상태 API를 조회한다.

긴 처리를 최초 HTTP 요청과 분리할 수 있지만, AI에 job 상태와 결과 보존, 결과 전달·재시도·중복 처리 경로가 필요하다. 현재는 Backend가 질문 상태를 소유하고 AI가 영구 저장하지 않는 책임 경계를 유지하려 하므로 채택하지 않는다. 60초 안에 처리할 수 없는 요청이 지속적으로 발생하면 재검토할 대안이다.

## Decision

**회의 QnA는 회의 분석 AI(analysis)에 배치한다. Backend가 `POST /v1/chat`을 호출하면 분석 AI가 최종 답변 또는 실패를 HTTP 응답으로 반환한다.**

기존 WebSocket 방식보다 연결 소유 인스턴스에 대한 의존과 녹음 프로토콜의 QnA 처리를 줄일 수 있다. HTTP 202 방식과 달리 AI에 영구 job 상태나 별도 결과 전달 경로도 필요하지 않다. 답변 생성 동안 HTTP 요청을 유지하는 비용과 타임아웃 조정은 감수한다.

V2의 확장 시나리오에 맞춰 특정 인스턴스의 녹음 연결을 경유하는 구조보다 요청별로 분석 AI 인스턴스를 선택하는 구조가 적합하다고 판단한다. HTTP QnA를 live에 두면 녹음과 LLM 작업이 같은 프로세스를 공유하고 Backend에 챗봇용 HTTP 주소가 추가로 필요하다. analysis에 배치해 녹음 연결의 안정성을 보호하고 기존 분석 HTTP 호출 경로를 재사용한다.

- analysis는 QnA·요약·화자 분리 HTTP 라우터와 챗봇 모델·Backend 조회 클라이언트를 소유한다. 조회 클라이언트는 앱 수명 동안 재사용하고 종료 시 닫는다.
- live는 녹음·전사 WebSocket을 제공하며 챗봇 라우터나 LLM·조회 클라이언트를 초기화하지 않는다.

- 요청은 camelCase JSON으로 `aiRequestId`, `meetingId`, `teamId`, `question`, `conversationHistory`, `transcriptSegments`를 전달한다. ID는 #71의 정수 계약을 따른다. 현재 질문은 `question`에만 넣으며, 화자 이름의 null과 답변 없는 이전 질문을 허용한다.
- 성공 응답은 HTTP 200과 `aiRequestId`, Markdown `answer`, `citations`를 포함한 JSON이다. 실패는 기존 오류 코드를 유지하며, 잘못된 요청·권한 문제는 4xx, 조회·생성 등 처리 실패는 5xx로 구분한다. 세부 상태 코드와 식별자를 읽을 수 없는 요청의 오류 형식은 API 계약에서 확정한다.
- AI의 자료 조회는 `/internal/v1/qna/**`와 서버 간 공유 키 인증을 유지한다. Backend가 `aiRequestId`를 기준으로 조회·공유 권한을 판단한다.
- 녹음 WebSocket의 `chat.*` 이벤트, 질문용 수신 한도 상향과 녹음 종료에 연결된 AI 질문 취소 처리는 제거한다. Backend는 종료 시 질문 취소·크레딧 복구를 처리하고 이후 도착한 결과를 무시한다.
- 회의당 활성 질문 제한과 질문 상태 관리는 Backend가 담당한다. AI에는 질문 중복 캐시나 자동 재전송을 추가하지 않는다.

## Consequences

### Positive

- 분산 환경에서 녹음 WebSocket을 소유한 인스턴스를 찾는 QnA 전달 경로가 필요 없어진다.
- V2에서 Backend·AI 인스턴스를 다중화할 때 QnA 요청을 녹음 연결 위치와 독립적으로 분산할 수 있다.
- 챗봇 모델·프롬프트 변경을 배포할 때 녹음 연결을 담당하는 live 프로세스를 재시작할 필요가 없다.
- Backend는 기존 분석 AI HTTP 주소로 QnA·요약·화자 분리를 요청한다.
- 질문 입력과 결과 전달을 녹음 이벤트에서 분리해 녹음 프로토콜과 연결 수명 관리를 단순화한다.
- 현재 Agent·조회 도구·근거 ID 검증을 재사용하고, HTTP 라우터와 요청·응답 스키마를 중심으로 변경할 수 있다.

### Negative

- QnA는 요약·화자 분리 요청과 같은 analysis 프로세스의 CPU·메모리·연결 자원을 공유한다. 분석 요청이 몰리면 챗봇 응답 지연에 영향을 줄 수 있다.
- analysis의 배포·장애는 챗봇과 종료 후 분석에 함께 영향을 준다.
- 일반 스레드에서 동기 HTTP 호출을 하는 경우, AI 응답을 기다리는 동안 호출 스레드와 Backend–AI HTTP 연결을 계속 점유해 스레드 풀과 HTTP 연결 풀의 가용 자원이 줄어들 수 있다.

---



## Reconsideration Conditions

- 긴 회의 입력에서 Backend의 대기 정책 내에 답변을 반환하기 어렵다는 측정 결과가 반복되면, 시간 정책 조정과 HTTP 202 기반 job 방식을 비교한다.
- AI가 영구 job 상태와 결과 전달 재시도를 소유하게 되면 callback 또는 polling 방식의 비용을 다시 비교한다.
- 답변의 스트리밍 출력이 요구사항이 될 경우 Backend–AI HTTP 스트리밍을 포함해 결과 전달 방식을 재검토한다.
- QnA와 종료 후 분석의 자원 경쟁으로 응답 지연 목표를 반복적으로 초과하거나 배포 주기를 분리할 필요가 생기면, QnA를 별도 서비스로 분리하는 방안을 검토한다.
