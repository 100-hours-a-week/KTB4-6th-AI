# ADR-0009: 녹음 원본을 어디에 보관했다가 녹음 파일로 저장할 것인가

## Status

Proposed (논의 중)

---

## Context

[ADR-0008](0008-live-audio-stream-decoder-and-ai-session-lifetime.md)에 따라 한 번의 회의는 여러 녹음 구간(MediaRecorder 수명주기)으로 나뉜다. 재연결이나 재개할 때마다 FE는 새 MediaRecorder를 만들고, 새 MediaRecorder는 헤더부터 다시 시작하는 새 녹음 구간을 만든다. 이 ADR은 녹음 도중 원본을 어디에 보관하고, 누가 여러 녹음 구간을 녹음 파일 하나로 만들어 S3에 올릴지 비교한다. 

현재 녹음 파일의 생성, 업로드 책임은 FE가 가지고 있다.

```text
[FE] MediaRecorder 청크를 메모리(recordedChunks)에 모음
  → 녹음 종료 시 Blob 하나로 합침 → ffmpeg.wasm으로 MP4(AAC) 변환
  → BE가 발급한 presigned URL로 S3 업로드 → BE AudioFile AVAILABLE
[BE] 사후 화자 분리가 AudioFile AVAILABLE을 기다렸다가 presigned 다운로드 URL을 Modal에 전달
```

- FE는 모든 청크를 `recordedChunks`에 넣고, WebSocket이 열려 있을 때만 전송한다. 끊긴 것을 감지하기 전까지 만든 청크는 녹음 파일에는 들어가지만 AI에는 가지 않는다. ([useMediaRecorder](https://github.com/100-hours-a-week/KTB4-6th-FE/blob/dev/src/features/recording/model/useMediaRecorder.ts), [recording-websocket-provider](https://github.com/100-hours-a-week/KTB4-6th-FE/blob/dev/src/features/recording-websocket/model/recording-websocket-provider.tsx))
- FE는 연결이 끊기면 `release()`를 호출해 `recordedChunks`를 비운다. 페이지가 새로고침되거나 종료돼도 메모리의 청크는 사라진다.
- 일시정지할 때 FE는 PATCH 응답을 받은 뒤 recorder를 멈추고, BE는 PATCH 처리 중 AI 연결 상태를 바꾼 뒤 도착한 청크를 AI로 보내지 않고 버린다. PATCH 왕복 시간만큼의 청크가 파일에만 들어간다. ([AiLiveMeetingConnection.forwardAudio](https://github.com/100-hours-a-week/KTB4-6th-BE/blob/dev/src/main/java/com/backend/meety/domain/ai/realtime/AiLiveMeetingConnection.java))
- 여러 MediaRecorder의 청크를 한 배열에 모아 Blob 하나로 만들면 헤더가 여러 번 들어간 파일이 된다. fragmented MP4는 이런 파일을 디코딩하면 스트림 경계마다 오디오 일부가 사라진다. 스트림을 따로 두고 concat 필터로 합치면 형식이 섞여도 손실이 없다. ([실험 요약](../../experiments/stream-concat-decoding/summary.md))
- 실시간 AI 서버는 현재 S3를 사용하지 않는다. S3 권한과 AudioFile은 BE가 관리한다.

---

## Decision Drivers

반드시 지켜야 하는 조건은 정하지 않았다. 아래 기준의 우선순위를 정하는 것이 이번 논의의 목적이다.

- **녹음 파일과 전사의 시간축이 맞는가?** 시간축의 어긋남이 1초 누적되면 화자 연결 정확도가 약 4%p, 2초 누적되면 약 12%p 하락했다. 0.3초 이하에서는 시간 가중 정확도 변화가 측정되지 않아 0.3\~0.5초 이하의 시간축 어긋남을 보장할 필요가 있다.
- **페이지가 죽어도 녹음이 남는가?** 모바일 새로고침, OS의 페이지 종료, 탭 닫기가 실제로 일어난다. "서버에 이미 보낸 녹음"만 남으면 되는지, "보내지 못한 녹음"까지 남아야 하는지에 따라 후보의 평가가 달라진다.
- **네트워크가 끊긴 동안의 소리를 녹음 파일에 남기는가?** 페이지는 살아 있고 네트워크만 끊긴 경우(데스크톱 Wi-Fi 끊김 등)에 해당한다.
- **프로토콜과 구현 복잡도가 늘지 않는가?** 청크별 ACK처럼 FE·BE 사이에 프로토콜 복잡도가 늘어나는 것을 고려해야 한다.
- **서버 부하와 동시 녹음 수에 영향이 적은가?** 녹음 원본을 서버 메모리에 쌓거나, 녹음마다 프로세스를 추가되어 동시 처리 가능한 녹음 수가 제한될 수 있다.

---

## Considered Options

### A. 현재 방식: FE 메모리에 보관하고 녹음 종료 시 FE가 업로드

FE가 청크를 메모리에 모았다가 녹음 종료 시 합쳐 변환하고 presigned URL로 올린다. 여러 녹음 구간을 다루려면 MediaRecorder마다 청크를 따로 모으고, 종료 시 ffmpeg.wasm의 concat 필터로 합쳐야 한다. 연결이 끊겨도 `release()`로 청크를 비우지 않도록 바꿔야 한다.

**장점**

- 서버, AI, 저장 흐름을 바꾸지 않는다. FE 변경만으로 여러 스트림을 지원할 수 있다.
- 페이지가 살아 있으면 네트워크가 끊긴 동안의 소리도 녹음 파일에 남는다.
- 서버 부하와 동시 녹음 수에 영향이 없다.

**단점**

- \*\*녹음 파일과 전사의 시간이 어긋난다.\*\* 끊김 감지 전 청크와 일시정지 처리 중 버려진 청크가 파일에만 들어가고, BE-AI 서버에는 전달되지 않는다. 모바일처럼 close 없이 끊기면 감지까지 수 초 이상 걸릴 수 있고, 한 번만 끊겨도 그 뒤 전사 전체가 2초 이상 밀려 화자 연결 정확도가 80% 아래로 떨어질 수 있다.
- 시간축 어긋남을 보정하기 위해서는 FE의 MediaRecorder, WebSocket의 정지·재개 순서를 바꾸고, 끊김이나 데이터 유실을 보정하기 위한 FE-BE 프로토콜을 추가해야 한다(ACK / 재연결 시 이전 구간의 바이트 수 확인 등)

- **페이지가 죽으면 녹음 전체가 사라진다.** 모든 청크가 메모리에만 있다.
- 긴 회의에서는 녹음 전체가 브라우저 메모리에 머문다(1시간 약 20\~90 MB). 종료 시 ffmpeg.wasm 변환에도 메모리가 추가로 든다. 
- 녹음 종료 후 브라우저에서 변환과 업로드가 끝날 때까지 사용자가 기다려야 한다.

### B. 브라우저 영속 저장소에 보관하고 FE가 업로드

FE가 청크를 IndexedDB 같은 브라우저 영속 저장소에 MediaRecorder별로 저장하고, FE가 업로드한다. 업로드 시점은 녹음 종료 시 일괄로 하거나, 각 녹음 구간이 끝날 때마다 나눠 올릴 수 있다. 연결 끊김 이후 연결이 복구되면 올리지 못한 녹음을 찾아 업로드를 이어 간다. 

**장점**

- **페이지가 새로고침되거나 종료돼도 저장해 둔 녹음이 남는다.** 사용자가 다시 열면 이어서 올릴 수 있다.
- 페이지가 살아 있으면 네트워크가 끊긴 동안의 소리도 녹음 파일에 남는다.
- 서버 부하와 동시 녹음 수에 영향이 없다.

**단점**

- **시간 어긋남은 A안과 같다.** 파일에만 있고 AI에는 가지 않은 청크가 그대로 남는다. A안의 두 가지 보정을 똑같이 해야 하며, 보정하면 끊긴 동안의 소리를 남기는 장점과 충돌한다.
- **FE 복구 흐름이 필요하다.** 재방문 시 올리지 못한 녹음 탐지, 업로드 재시도, 올린 뒤 로컬 삭제, 여러 탭이 동시에 열린 경우 처리가 추가된다.
- **연결 끊김 이후 사용자가 페이지를 다시 열지 않으면 파일이 업로드되지 않는다.** 서버는 녹음 파일이 오기를 기다리기만 할 수 있다.
- 청크(20ms 간격)마다 저장소에 쓰면 부담이 크므로 묶어서 써야 한다. 페이지가 갑자기 죽으면 마지막 묶음은 잃는다.

### C. 서버가 AI로 전달된 청크를 저장

BE가 AI로 전달에 성공한 청크만 녹음 구간별로 디스크에 이어 쓰거나, AI가 디코더에 넣는 청크를 디스크에 이어 쓴다. 녹음 구간이 끝나면 S3에 올리고, 녹음 세션이 끝나면 구간들을 concat 필터로 합쳐 녹음 파일 하나를 만든다. FE는 녹음 파일을 보관하거나 올리지 않는다.

저장 주체에 따라 두 가지 변형이 있다.

- **C1. BE가 저장**: BE가 녹음 구간을 저장해 S3에 올리고, 녹음이 끝나면 BE가 직접 병합해 녹음 파일을 올린다. BE–AI 사이에 새 메시지가 필요 없고 AI에 S3 권한도 필요 없지만, BE에 ffmpeg가 필요하다.
- **C2. AI가 저장**: AI가 스트림을 저장·업로드하고 병합한다. AI에 S3 쓰기 권한이 필요하다.

```text
[녹음 중] 서버: 전달된 청크 → 로컬 파일 → 스트림 종료 시 S3 (recordings/.../streams/{순번})
[녹음 종료] 스트림들을 concat 필터로 합침 → 녹음 파일 S3 업로드 → BE AudioFile AVAILABLE
```

**장점**

- **녹음 파일과 전사의 시간이 구조적으로 맞는다.** 파일로 합치는 바이트와 AI가 처리한 바이트가 같다. 보정이 필요 없다.
- **페이지가 죽어도 서버에 이미 도착한 녹음은 남는다.**
- FE가 단순해진다. 녹음 파일 보관, ffmpeg.wasm 변환, presigned 업로드, 녹음 종료 시 변환 대기가 빠진다.
- 청크는 이미 서버로 가고 있으므로 추가 전송량이 없다. FE–BE 프로토콜도 바뀌지 않는다.
- 녹음 종료 이후 사용자가 파일 업로드 시간을 기다릴 필요가 없다.

**단점**

- **서버에 도착하지 못한 소리는 녹음 파일에도 없다.** 페이지가 살아 있어도, 네트워크가 끊긴 동안의 소리는 남지 않는다.
- 서버 디스크를 쓴다. 메모리가 아니라 디스크에 이어 쓰면 동시 녹음 20개 × 1시간 기준 최대 약 2 GB이고, 스트림이 끝날 때마다 업로드 후 삭제한다.
- 병합이 실패했을 때의 재시도 방법을 정해야 한다. C2는 합치기 완료 알림(`audio.stored` 등) 메시지가 BE–AI 사이에 추가된다.
- 저장하던 서버(BE 혹은 AI)가 죽으면 아직 올리지 않은 진행 중 녹음 구간 하나를 잃는다.
- C1은 BE가 오디오 파일 쓰기, 업로드, 병합을 모두 맡는다. BE 배포 이미지에 ffmpeg가 필요하고, 음성 처리 책임을 AI에 두는 [ADR-0006](0006-live-audio-decoding-location.md)의 경계와 달라진다. C2는 AI에 S3 권한을 새로 줘야 한다.
