# ADR-0009: 녹음 원본은 브라우저에 보관하고 FE가 병합·업로드한다

## Status

Accepted

---

## Context

[ADR-0008](0008-live-audio-stream-decoder-and-ai-session-lifetime.md)에 따라 BE–AI WebSocket과 AI 세션은 회의 시작부터 종료까지 유지하고, FE–BE 재연결이나 녹음 재개 시 새 MediaRecorder 스트림을 시작한다. 따라서 회의 녹음은 여러 독립된 스트림으로 나뉠 수 있다. 이 원본들을 어디에 보관하고 누가 최종 녹음 파일을 만들어 업로드할지 결정해야 한다.

기존 방식은 FE가 MediaRecorder 청크를 메모리에 모으고, 녹음 종료 시 브라우저에서 MP4(AAC)로 변환해 BE가 발급한 presigned URL로 업로드하는 것이다. 메모리만 사용하면 페이지 새로고침·종료 시 원본이 사라지고, FE–BE 연결이 끊겼을 때 FE에 남은 청크와 AI가 받은 청크가 달라질 수 있다. 녹음 파일과 전사의 입력이 달라지면 이후 화자 연결에 사용하는 시간축도 어긋날 수 있다.

복구 설계에서는 BE–AI 구간의 Audio 유실이 없다고 가정하고, FE–BE 단절로 전달되지 못한 청크를 복구 대상으로 삼는다. 이전 MediaRecorder의 미ACK 청크를 먼저 복구한 뒤 AI의 디코더를 초기화하고 새 스트림을 시작해야 한다. 새 디코더에 이전 스트림의 나머지 바이트를 보내서는 안 된다. 녹음기가 멈춘 동안 생성되지 않은 소리를 복구하는 것은 이 범위에 포함하지 않는다.

여러 MediaRecorder 스트림은 각각 컨테이너 헤더를 갖기 때문에 하나의 Blob으로 단순 연결하는 대신 스트림별로 디코딩해 오디오를 병합하는 방식이 필요하다. 파일 업로드 권한과 상태는 BE가 관리하며, 실시간 AI는 현재 S3 파일 저장을 담당하지 않는다.

---

## Decision Drivers

- **녹음 파일과 전사의 입력을 맞출 수 있는가?** FE–BE 단절로 미전달된 청크를 식별·재전송하고, 이전 스트림 복구 이후 새 스트림으로 전환할 수 있어야 한다.
- **페이지 새로고침·종료에 대비해 원본을 보존할 수 있는가?** 페이지 메모리가 사라져도 저장 완료된 원본을 다시 읽을 수 있어야 한다.
- **기존 파일 처리 책임과 서버 운영 부담을 유지할 수 있는가?** FE의 변환·업로드 경로를 재사용하는 비용과 서버에 저장·병합·업로드를 추가하는 비용을 비교한다.
- **분산 환경에서 진행 중 파일의 위치를 관리해야 하는가?** 서버 인스턴스별 로컬 파일과 장애 복구 상태를 추가하는 부담을 고려한다.

---

## Considered Options

### A. FE 메모리에 보관하고 FE가 업로드

FE가 청크를 메모리에 스트림별로 모아 녹음 종료 시 병합·변환하고 업로드한다. 순번과 ACK를 추가하면 페이지가 살아 있는 동안 미확인 청크를 재전송할 수 있다.

**장점**

- 기존 FE 업로드 경로를 유지하며 브라우저 영속 저장소 관리가 필요 없다.
- BE·AI에 원본 파일 저장과 병합 작업을 추가하지 않는다.

**단점**

- 페이지 종료·새로고침으로 메모리가 사라지면 원본과 미확인 청크를 복구할 수 없다.
- 긴 회의의 원본 전체가 브라우저 메모리에 머물고, 종료 시 변환에도 추가 메모리가 필요하다.

### B. 브라우저 영속 메모리에 보관하고 FE가 업로드

FE가 영속 메모리에 청크 순번·스트림 구분·ACK 상태와 원본을 보관한다. 재연결 시 미확인 청크를 복구하고, 녹음 종료 시 저장된 스트림을 읽어 병합·변환한 뒤 업로드한다.

**장점**

- 페이지 메모리와 독립적으로 저장 완료된 원본을 보존하고 재연결 시 미확인 청크를 읽을 수 있다.
- 같은 원본을 실시간 전송 복구와 최종 파일 생성에 사용할 수 있다.
- 기존 FE 업로드 경로를 유지하고 BE·AI에 원본 파일 저장·병합 작업을 추가하지 않는다.

**단점**

- FE에 저장소 쓰기, ACK 상태 관리, 재전송, 업로드 재시도와 로컬 정리 흐름이 필요하다.
- 저장소 용량 제한·삭제·쓰기 실패에 대비해야 하며, 저장 완료 전 페이지가 종료되면 청크가 유실될 수 있다.
- 변환·업로드가 브라우저 성능과 네트워크에 의존한다. 사용자가 다시 접속하지 않으면 서버가 로컬 원본을 회수할 수 없다.

### C. BE 또는 AI가 원본을 저장·병합·업로드

서버가 AI로 전달하는 청크를 스트림별 파일로 저장하고, 녹음 종료 시 병합해 업로드한다.

**장점**

- 페이지 종료 이후에도 서버에 도착한 원본으로 파일을 준비할 수 있다.
- 서버에 저장하는 청크와 AI로 전달하는 청크를 일치시키는 구조를 만들 수 있다.
- 브라우저에서 전체 파일을 변환·업로드하는 부담이 줄어든다.

**단점**

- 서버에 파일 저장·병합·업로드와 실패 복구 책임이 추가되고 디스크·변환 자원을 사용한다.
- 분산 환경에서 진행 중 파일의 위치와 저장 담당 인스턴스 장애 시 복구를 관리해야 한다.
- 서버 저장만으로 FE–BE 단절 구간의 미전달 청크가 복구되지는 않는다. 이 구간까지 보존하려면 FE의 보관·재전송이 별도로 필요하다.
- BE가 병합하면 음성 파일 처리 도구가 BE 배포에 추가되고, AI가 업로드하면 AI에 S3 쓰기 권한과 BE 완료 통지가 추가된다.

---

## Decision

**B안을 선택한다. 녹음 원본은 FE가 영속 메모리에 스트림별로 보관하고, FE가 최종 파일을 병합·변환해 BE가 발급한 presigned URL로 업로드한다.**

A안은 페이지 수명에 원본 보존이 묶여 새로고침 이후 복구 요구를 충족하지 못한다. C안은 서버에 도착한 원본을 보존할 수 있지만, FE–BE 단절 구간까지 복구하려면 FE의 보관·재전송이 여전히 필요하다. 따라서 브라우저에 원본을 보관하는 복구 흐름을 파일 생성에도 활용하고, 서버에 별도의 원본 저장·병합 책임을 추가하지 않는 B안을 선택한다. FE 복구 구현의 복잡도와 최종 파일 준비가 브라우저에 의존하는 비용을 감수한다.

처리 순서는 다음과 같이 정한다.

1. FE는 청크에 세션 전체의 순번과 MediaRecorder별 스트림 구분을 부여하고 영속 메모리에 보관한다. ACK된 청크도 최종 파일 업로드가 완료될 때까지 유지한다.
2. BE는 AI로 전달한 청크의 처리 순번을 관리하고 누적 ACK를 보낸다. 재전송된 청크는 순번으로 중복을 판별해 AI에 중복 전달하지 않는다.
3. FE–BE 연결이 끊기면 기존 MediaRecorder를 멈추고 마지막 청크까지 보관한다. BE–AI 연결과 이전 스트림의 디코더는 복구 동안 유지한다.
4. 재연결 시 이전 스트림의 미ACK 청크를 먼저 재전송한다. 복구 완료 이후 BE가 AI에 `decoder.reset`을 보내고 `decoder.ready`를 확인한다. FE는 `stream.ready` 이후 새 MediaRecorder 스트림의 녹음을 시작한다.
5. 녹음 종료 시 FE가 저장된 스트림을 순서대로 읽어 ffmpeg.wasm의 concat 필터로 병합하고 MP4(AAC)로 변환한다. BE에서 presigned URL을 발급받아 업로드한 뒤 완료 API를 호출한다.
6. 업로드와 완료 처리가 성공하면 FE가 로컬 원본을 정리한다. BE는 업로드 권한과 파일 상태를 관리하고, 실시간 AI에는 원본 저장·병합·업로드 책임을 추가하지 않는다.

---

## Consequences

### Positive

- 브라우저에 보관한 원본을 미확인 청크 복구와 최종 파일 업로드에 함께 사용할 수 있다.
- 저장 완료된 원본은 페이지 메모리가 사라진 이후에도 복구에 사용할 수 있다.
- 서버에 원본 파일을 보관할 디스크, 병합 작업과 파일 위치 관리 구조를 추가하지 않는다.
- 이전 스트림 복구와 새 디코더 시작 순서를 명시해 파일과 AI 입력의 누락·중복을 줄일 수 있다.

### Negative

- FE는 저장소 실패, 재연결·재전송, 마지막 청크 저장, 업로드 재시도와 원본 정리까지 관리해야 한다.
- 브라우저 데이터 삭제나 저장 실패로 원본이 사라질 수 있으며, 업로드 전 사용자가 돌아오지 않으면 서버에서 파일을 확보할 수 없다.
- BE–AI 무손실은 복구 범위를 정하기 위한 가정이다. 서버 장애와 해당 구간의 유실까지 포함한 복구는 별도 설계가 필요하다.

---

## Reconsideration Conditions

- 실제 모바일·장시간 녹음에서 브라우저 저장소 또는 병합 메모리 문제로 파일 준비가 반복 실패하면 구간별 업로드나 서버 병합을 비교한다.
- 사용자의 재방문 없이 녹음 파일을 서버에서 확보해야 하는 요구가 생기면 서버 저장 또는 녹음 중 구간 업로드를 재검토한다.
- 복구 후 녹음 파일과 AI 입력의 누락·중복·시간축 불일치가 관측되면 마지막 청크 저장, ACK 기준과 디코더 전환 순서를 점검한다.
